# Aion DocMind 客户端能力增强建议

状态：建议稿，供 Aion 维护者评审；尚不代表已实现或已发布的公共契约。

更新日期：2026-09-14。

适用范围：`aion.aliyun.docmind` 的文档解析客户端，以及依赖该客户端的通用应用场景。本文依据查阅的 Aion 封装源码和阿里云官方文档整理；示例中的新增类型、方法和参数均为设计建议。

## 1. 建议目标

建议由 Aion 完整封装 DocMind 请求模型、运行时配置、提交、查询、轮询及异常转换，使调用方通过公开接口控制等待时间和重试行为，无需了解阿里云 SDK 的内部对象。

查阅的 Aion 封装已经提供 `submit_local_file()`、`submit_online_file()`、`get_result()` 和 `get_text()`。其中 `get_result()` 持续轮询直到任务完成；现有公开签名没有提供总等待时限、单次请求超时或独立的单次查询入口。建议在这些基础能力上补齐控制面，保持已有调用方式兼容。

以下依赖及其对象转换应保留在 Aion 内部：

- `alibabacloud_docmind_api20220711.models`：构造本地文件提交、在线文件提交和任务查询请求。
- `alibabacloud_tea_util.models`：构造超时、自动重试等运行时选项。
- 底层 SDK 客户端的方法选择、参数映射和响应解析。

调用方应使用 Aion 自己定义的配置、结果和异常类型，不必通过继承客户端、重写提交方法或访问底层 `client` 对象来获得这些通用能力。该建议仅针对 DocMind，不要求同步重构其他模型客户端或引入全库统一重试框架。

## 2. 能力与实用场景

| 建议能力 | 实用场景 | 调用方获得的收益 |
|---|---|---|
| 公开连接与读取超时 | 上传解析、网络质量不稳定的服务 | 能按运行环境设置请求等待边界，避免重复封装 SDK |
| 单次查询与有限时轮询分离 | Web 服务、后台任务、命令行工具 | 分别支持立即查询和等待完成，调用方式符合执行环境 |
| 区分提交重试与查询重试 | 大文件上传、成本敏感的批量解析 | 查询可容忍短暂故障，提交结果不明时避免盲目创建重复任务 |
| 稳定异常与提交结果分类 | 自动化任务、故障诊断和人工核查 | 能区分未发出请求、明确拒绝、结果未知和已知任务查询失败 |
| 保留结构化结果和原始状态 | 版面处理、表格提取、全文索引 | 文本转换失败时仍能使用或检查已取得的解析数据 |
| 异步入口及明确的取消语义 | 异步服务、多个文档并发解析 | 不阻塞事件循环，能够释放本地等待资源 |
| 可选依赖隔离与诊断信息 | 仅使用部分 Aion 能力的应用 | 降低安装耦合，便于在不暴露文档内容的前提下定位失败 |

## 3. 核心功能建议

### 3.1 提供 Aion 自有的请求配置

建议通过 `DocMindRequestOptions` 等公开类型提供连接和读取超时，支持客户端默认配置与单次调用覆盖。推荐优先级为：本次调用显式配置、客户端配置、Aion 已公布的默认值。单次覆盖不应修改共享客户端的配置，避免并发请求互相影响。

阿里云 Python SDK V2.0 可通过 `RuntimeOptions` 设置请求级超时，其时间单位为毫秒。建议 Aion 对外统一使用秒，由内部完成单位转换；不要要求调用方直接传入 `RuntimeOptions`。[阿里云 SDK 超时机制](https://help.aliyun.com/zh/sdk/developer-reference/configure-a-timeout-period)

建议明确区分以下时间概念：

| 参数或概念 | 建议含义 |
|---|---|
| `connect_timeout` | 单次网络连接的等待限制，单位秒 |
| `read_timeout` | 单次网络读取的等待限制，单位秒；以底层传输的具体语义为准 |
| `poll_interval` | 任务尚未完成时，两次查询之间的等待间隔，单位秒 |
| `wait_for_result(..., timeout=...)` | 本次等待结果的总预算，包含查询、查询重试及间隔等待，单位秒 |

超时和间隔应校验为有限正数；未传入配置表示继承默认值，不把 `0` 隐式解释为无限等待。单次网络超时与整个任务的等待预算是不同的限制，文档和异常中都应区分。

本地文件和在线文件应遵循一致的配置规则。高级上传可能涉及辅助请求、文件传输和正式任务提交，实现时应逐项验证配置是否生效，不能只设置最外层运行时对象就宣称整个提交过程已被限时。

### 3.2 将单次查询和等待完成分开

建议新增两个职责清晰的方法：

- `query_result(task_id, ...)`：执行一次逻辑查询，返回当前任务快照；允许在查询重试策略范围内重试传输错误，但不因任务尚未完成而内部轮询。
- `wait_for_result(task_id, *, timeout, poll_interval=1.0, ...)`：在明确预算内重复调用查询能力，直到取得终态或达到等待边界。新方法要求调用方给出有限的总等待时间。

`get_result()` 保留原有兼容入口；内部可复用相同查询与结果转换逻辑，避免出现两套状态判断。已经取得任务 ID 的调用方，可以在另一次调用中继续查询该任务，无需重新提交文件；可查询范围和结果保留期限仍取决于上游服务契约。

这使命令行工具能够直接等待完成，也使 Web 服务或后台调度器能够自行安排查询频率、持久化任务 ID 和决定何时再次检查。

### 3.3 让轮询预算覆盖实际等待

建议使用单调时钟计算截止时间；每次查询、重试和休眠前检查剩余预算，并将休眠时间及可控制的网络请求预算限制在剩余时间内。正常的“任务仍在处理中”属于轮询，不应消耗传输错误的重试次数；两者都必须计入本次总等待时间。

仅在循环开始处检查时间不足以保证及时返回：最后一次网络请求仍可能长期阻塞。需要结合底层网络操作可支持的截止或取消能力实现。若底层只能提供连接与读取超时，应公布可能超过总预算的边界，不能把一个循环计时器描述为可强制中断所有 I/O 的硬截止。

达到等待预算后，抛出包含任务 ID、实际耗时和最后已知状态的 `DocMindWaitTimeout`。它只表示本次等待结束，不表示远端解析失败或远端任务已取消，也不能触发隐式重新提交。

### 3.4 按操作区分重试策略

阿里云 SDK 提供 `autoretry`、`max_attempts` 等运行时配置。建议 Aion 显式管理有效策略及其计数语义，并测试实际请求次数，避免 Aion 重试与底层 SDK 重试叠加。[阿里云 SDK 重试机制](https://help.aliyun.com/zh/sdk/developer-reference/configure-a-retry-mechanism)

建议采用以下默认原则：

| 操作 | 建议行为 |
|---|---|
| 提交任务 | 默认只尝试一次。失败后的动作取决于是否能确认远端没有受理 |
| 查询任务 | 允许调用方启用有限重试，针对可恢复的传输错误执行退避，始终遵守剩余时间预算 |
| 已知任务仍在处理 | 继续按轮询间隔查询，不重新提交 |
| 远端任务明确失败 | 返回失败终态，不通过查询重试掩盖，也不自动创建新任务 |
| 提交结果不明 | 返回明确的未知提交异常，由调用方决定核查和后续动作 |

`max_attempts` 建议统一定义为包含首次请求的总尝试次数，`1` 表示不重试；内部负责转换 SDK 语义，不让调用方猜测底层参数是否包含首次请求。可分别提供提交和查询策略，但“允许更多尝试”不等于授权重放结果未知的提交。

提交超时或响应丢失时，远端可能已经创建任务。仅在能够证明请求尚未发出、上游明确保证本次未受理，或上游提供并正确使用了幂等机制时，才考虑自动重试提交。不能仅凭异常名称、HTTP 状态码类别或本地生成的请求标识推导出提交幂等性。

如果上游没有提供按调用方标识找回任务的能力，Aion 应明确说明“无任务 ID 时无法自动确认远端结果”的限制，而不是承诺一定能够恢复或绝不重复执行。

### 3.5 提供稳定、可判断的异常

建议定义 `DocMindError` 基类，并保留原始异常链。调用方应通过异常类型和字段判断，不必解析中文或英文错误消息。建议分类如下，具体命名可由维护者统一：

| 异常类型建议 | 语义 | 典型处理场景 |
|---|---|---|
| `DocMindInputError` | 提交前的参数或本地文件校验失败，请求尚未发出 | 修正路径、格式或参数后再次调用 |
| `DocMindSubmissionRejectedError` | 有可靠依据确认上游拒绝了本次提交，未创建解析任务 | 根据上游错误修正输入、权限或等待条件 |
| `DocMindSubmissionUnknownError` | 请求可能已被受理，但无法确认提交结果 | 保留诊断信息并核查，避免盲目重复提交 |
| `DocMindQueryError` | 已知任务的查询请求失败，无法取得本次快照 | 按查询策略重试；不据此认定解析失败 |
| `DocMindWaitTimeout` | 本次等待预算耗尽 | 稍后使用同一任务 ID 查询 |
| `DocMindTaskFailedError` | 便利接口要求成功内容，但远端任务明确失败 | 展示失败原因，调用方决定是否另开任务 |
| `DocMindResultDecodeError` | 上游响应结构或文本转换不符合预期 | 使用保留的原始数据诊断或执行其他转换 |

异常建议按可取得的信息携带 `operation`、`task_id`、`request_id`、`provider_code`、`http_status`、`submission_state`、`elapsed_seconds` 和最后一次任务快照；没有的信息使用空值，不能伪造。`submission_state` 只用于提交相关错误，可区分 `not_sent`、`rejected`、`unknown`，并允许在已知任务 ID 后保留已受理事实。

不建议只暴露一个笼统的 `retryable` 布尔值：查询可重试与提交可安全重放是不同问题。若提供重试建议，应指明针对何种操作、在什么前提下适用。

异常转换不能假设所有 Python 异常都有 `.message` 属性；应保留原异常为 `__cause__`，并使用可靠的消息提取方式，避免二次异常掩盖真正的失败。

### 3.6 返回稳定快照，保留原始解析数据

建议新增 Aion 自有的 `DocMindTaskSnapshot`。单次查询和等待方法都返回该快照；等待方法在得到成功或失败终态时返回，在传输失败、协议异常或本地等待超时时抛出对应异常。便利方法 `get_text()` 再将明确的任务失败转换为 `DocMindTaskFailedError`。

阿里云结果中的 `Completed` 表示任务是否结束，结束状态还需通过 `Status` 区分成功和失败，因此不能把完成直接映射成成功。[DocMind 文档智能解析接口](https://help.aliyun.com/zh/document-mind/developer-reference/docstructure)

| 建议字段 | 含义 |
|---|---|
| `task_id` | 本次查询的远端任务 ID |
| `state` | Aion 归一化状态，例如 `processing`、`succeeded`、`failed`、`unknown` |
| `completed` | 上游是否明确给出完成标志；无法确定时为空 |
| `provider_status` | 上游原始状态，方便诊断和后续兼容 |
| `data` | 保留完整结构化解析数据，不只保留拼接后的文本 |
| `text` | 成功提取的文本；无法提取时为空，合法空文本与提取失败要区分 |
| `text_error` | 文本提取失败信息，与远端任务状态独立 |
| `error` | 已知远端任务失败的错误信息，成功任务为空 |
| `request_id` | 当前查询的上游请求标识，若上游提供 |

远端解析成功但本地文本拼接失败时，应保留成功的远端状态和原始 `data`，记录 `text_error`；需要纯文本的便利接口可以抛出携带快照的 `DocMindResultDecodeError`。这样全文索引调用方能够明确失败，版面处理调用方仍可利用结构化结果。

单次查询遇到无法识别的状态时，应保留原始信息并标为 `unknown`；等待方法不得据此猜测成功或持续无限轮询，应给出携带快照的协议解析异常。缺失字段、相互矛盾的状态也应明确处理。

## 4. 建议接口示意

以下代码用于评审接口可用性，不能直接当作当前 Aion 的可执行示例。类型名称、导出位置和默认值以最终发布契约为准。示例中的数值仅用于说明配置方式。

```python
from aion.aliyun.docmind import DocMindClient
from aion.types import DocMindRequestOptions
from aion.types import DocMindRetryPolicy


client = DocMindClient(
    access_key_id=access_key_id,
    access_key_secret=access_key_secret,
    endpoint=endpoint,
    request_options=DocMindRequestOptions(
        connect_timeout=5.0,
        read_timeout=20.0,
    ),
    retry_policy=DocMindRetryPolicy(
        submit_max_attempts=1,
        query_max_attempts=3,
    ),
)

task_id = client.submit_local_file("example.pdf")

# 方案一：查询当前状态，由调用方决定下一次查询时间。
snapshot = client.query_result(task_id)

# 方案二：等待终态；成功和失败都通过快照表达。
result = client.wait_for_result(
    task_id,
    timeout=120.0,
    poll_interval=2.0,
)
```

两种查询方式用于不同场景，无需每次都先查询再等待。`submit_online_file()` 应接受相同的可选请求配置；各方法允许仅关键字的调用级覆盖，未设置的字段继承客户端配置。示例未展示的超时和异常处理应按第三节契约完成。

公共类型建议从 Aion 的稳定类型入口导出；其定义应独立于阿里云 SDK 模型，导入这些类型不应强制加载 DocMind 依赖。

## 5. 后续增强建议

### 5.1 同步与异步接口保持一致

异步提交、查询和等待可作为第二阶段能力，建议沿用 Aion 的 `_async` 命名方式。优先封装底层可用的异步 SDK 方法，异步等待使用可取消的非阻塞休眠；同步和异步路径共用配置校验、状态归一化和异常转换。

取消本地等待不等于取消远端任务。提交时被取消也可能产生结果未知的情况，不应自动重放；应保留已获得的任务 ID 并正确传播取消。若某些 SDK 路径只能借助线程包装，应明确其限制：取消协程等待不能保证立即终止线程中的同步网络调用。

同时提供明确的资源释放方式，例如同步 `close()` 和异步 `aclose()`，并验证其底层支持范围；客户端关闭失败不应覆盖原有调用异常。

### 5.2 提供轻量诊断信息

建议允许调用方获取操作名、任务 ID、上游请求 ID、实际请求次数、耗时和归一化状态，用于记录日志或接入监控。配置重试后，应能知道实际发生了多少次请求，而不是只知道最终结果。

默认日志不输出文档全文、文件内容、访问密钥或带签名的完整 URL。完整响应可作为返回值或异常附带信息供调用方自行处理，不自动写入全局日志。诊断不强制绑定特定监控或日志平台。

### 5.3 保持可选依赖边界

DocMind 相关 SDK 由 Aion 的对应可选依赖组管理；启用文档解析时安装完整依赖，未启用时不影响其他 Aion 能力。缺少依赖时，应在使用 DocMind 能力处给出清晰安装提示。

建议公布验证过的 SDK 版本范围，并测试最小安装、对应可选依赖安装和构建产物导入。调用方不应为了配置超时，再自行安装和直接依赖底层 SDK。

## 6. Aion 与调用方的职责边界

| 事项 | Aion 负责 | 调用方负责 |
|---|---|---|
| 请求构造 | SDK 模型、运行时参数、文件资源释放、响应转换 | 提供合法输入与访问配置 |
| 等待控制 | 单次请求限制、一次等待调用的预算、取消传播 | 整个应用流程的执行时限和调度方式 |
| 重试 | 明确操作语义、受控传输重试、禁止未知提交的隐式重放 | 失败后的业务决策及重新提交授权 |
| 状态恢复 | 通过已知任务 ID 查询，返回稳定状态与诊断字段 | 任务 ID 保存、跨进程恢复、人工核查 |
| 数据处理 | 保留原始解析数据，提供通用文本提取 | 领域数据转换、内容校验和最终存储 |
| 幂等 | 如上游确有支持，提供明确的公开参数与能力说明 | 业务去重策略和持久化协调 |

Aion 不应内置数据库、消息队列、定时任务服务或特定应用的恢复规则，也不应自行清理调用方数据。它应提供足够可靠且可观察的基础能力，使调用方能够独立选择这些策略。

## 7. 兼容与实施顺序

建议按两个阶段推进，由维护者评审后确定具体发布版本。

第一阶段补齐公开请求配置、单次查询、有限时等待、稳定异常和结果快照。这些能力能直接减少调用方对 SDK 内部结构的依赖。内部先复用一套请求与结果转换逻辑，不必引入额外框架。

第二阶段补齐异步入口、资源释放和诊断扩展，并加强可选依赖与版本组合验证。第一阶段不能依赖第二阶段才能获得清晰的错误语义。

兼容原则如下：

1. 保留 `DocMindClient` 既有导入路径、已有位置参数，以及提交方法返回字符串任务 ID 的约定；新增配置采用可选的仅关键字参数。
2. 新查询和等待方法使用新快照类型；`get_result()` 保留已有字典结构，避免把类型升级直接传递给现有调用方。
3. 不在补丁版本中静默改变旧方法的默认等待时长、重试次数或失败返回方式。新方法明确采用有限时契约，旧行为变更应另行说明迁移步骤和适用版本。
4. 新方法先采用稳定异常体系；旧方法的异常和失败字典应通过兼容层维持既有约定。需要改变已公开行为时，单独标明破坏性变更。
5. 发布文档分别标注现有能力、新增能力及未支持能力，提供从旧方法迁移到新方法的示例，避免建议接口被误认为当前可用。

## 8. 建议验收标准

实现后，至少通过以下离线测试，并将真实服务验证单独记录：

- 本地文件与在线文件均可通过 Aion 公开参数配置超时；请求覆盖不污染客户端默认值，并验证 SDK 辅助上传步骤的配置传递。
- 单次查询在任务处理中立即返回快照；等待方法复用同一状态转换，正确区分成功、失败、处理中和未知状态。
- 假时钟验证查询、退避和休眠计入总预算；慢网络测试验证实际返回边界，明确底层不可中断部分的限制。
- 提交默认不重试；结果未知时，即使配置更多提交尝试也不盲目重放。查询重试次数与公布语义一致，SDK 内层没有额外放大请求数量。
- 查询超时仍保留任务 ID，后续可再次查询；单纯查询失败不会转成任务失败或触发重新提交。
- 覆盖本地校验失败、明确拒绝、响应丢失、无任务 ID、限流、远端失败、未知状态和响应格式异常；异常链和可取得的上游标识均保留。
- 远端解析成功但文本提取失败时，原始数据与远端成功状态仍可恢复；便利文本接口明确失败，不返回伪造的空成功结果。
- 原有四个方法的导入、调用参数和返回形状保持兼容；缺少 DocMind 可选依赖不影响无关能力和公共类型导入。
- 异步能力交付时，验证事件循环不被同步轮询阻塞、取消正确传播、资源释放以及线程兼容路径的已知限制。
- 真实服务补验使用受控文档，分别验证本地上传、在线文件、任务状态变化和 SDK 实际超时行为；涉及故障注入或重复提交的验证应控制调用次数与成本。

验收的核心是：调用方仅依赖 Aion 的公共接口，就能完成提交、查询、限时等待和失败判断；不需要自行构造阿里云请求模型或运行时选项。
