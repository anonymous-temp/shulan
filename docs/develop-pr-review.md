# develop 分支 PR 审核规范

适用于所有目标为 `develop` 的 PR，包括功能、修复、重构、文档、Report 协作及多智能体产出的改动。**审核人每次审核及复审均必须读取本文件的当前内容，逐项核对并在 PR 中留下审核记录。** 不得仅凭作者说明、旧审核结论或部分测试通过即批准合并。

本文件将 [贡献指南](../CONTRIBUTING.md) 的要求落实为审核步骤，不替代贡献指南。规则调整时两份文档须同步；发现不一致时先澄清并修正文档，不自行选择较宽松的要求。本文件规定人工与智能体审核流程，不代表已配置 Gitee 分支保护或自动检查。

## 1. 审核前准备

1. 阅读本文件和 [贡献指南](../CONTRIBUTING.md) 的当前版本，查看 [TODO.md](../TODO.md)、[ISSUE.md](../ISSUE.md) 中与本次任务相关的决策、风险和交接记录。
2. 确认 PR 目标为 `develop`，记录 PR 链接、源分支、当前源提交 SHA、作者声明的分支创建基线，以及审核时的 `develop` 提交 SHA。
3. 阅读 PR 的全部提交和相对 `develop` 的完整差异，核对修改内容与声明范围；审核不能仅覆盖作者特别指出的几个文件。
4. 按涉及内容补读 [测试规范](../tests/README.md)、[API 文档编辑手册](api/API_EDITING_GUIDE.md) 和相关架构文档；Report 协作还须核对 [Report Git 提交流程](report-git-workflow.md)。
5. 若在本地验证，使用对应源提交的干净工作区或独立 worktree，保护已有未提交改动；记录实际验证的提交与环境，避免测试了其他分支或混入本地修改。

## 2. 强制审核清单

下列要求必须逐项核对。分支、PR 目标、职责范围和全量测试不可标记为“不适用”；只有确实不存在跨模块依赖时，交接项才可注明“不适用”并说明原因。

### 2.1 分支来源与 PR 流程

- [ ] 源分支是基于创建时最新的 `develop` 新建的独立任务分支，符合贡献指南的命名规则；Report、hotfix 同样适用。
- [ ] PR 目标为 `develop`，没有通过直接推送或本地合并后直推绕过评审。
- [ ] 作者提供的创建基线与提交图、完整差异相符，没有夹带其他任务分支尚未合入的实现。

Git 提交关系只能辅助核对来源，单凭分支名称、共同祖先或“`develop` 是祖先”不能证明分支最初从何处创建。来源不清时要求作者补充基线与创建说明，不能把推测写成已核实。

### 2.2 单分支职责范围

- [ ] 本分支只实现一个模块或边界明确的一部分，实际差异与 PR 声明一致。
- [ ] 配套测试、接口文档及必要接线服务于同一目标，没有夹带独立功能、其他模块的实现或无关格式化。
- [ ] 修改共享文件时只涉及当前职责范围，没有覆盖他人工作；确需其他模块支持的部分按 2.4 节交接。

模块边界按业务职责判断，不按目录数量机械判断；同一功能的业务代码、测试和文档分布在多个路径并不自动构成违规。

### 2.3 全量离线单元测试

- [ ] 提交 PR 前已完成 `tests/unit/` 全量离线单元测试，结果全部通过；仅文档 PR 同样遵循此要求。
- [ ] 记录包含执行命令、执行环境、完成时间、结果摘要和对应源提交；审核人能够查看完整结束结果，不能只有“已测试”的声明。
- [ ] 测试实际覆盖完整离线收集范围，没有用单个文件、`-k` / `-m` 等筛选后的结果替代全量结果。
- [ ] 没有通过删除有效用例、放宽断言或新增无依据的跳过条件规避失败；既有合法跳过或预期失败须如实记录，并核对新增变化的原因。
- [ ] 结果对应当前待合并内容。评审修改、依赖合入、同步基线或解决冲突后，已重新完成全量测试并更新记录。

在项目根目录、`shulan` Conda 环境中执行：

```bash
conda activate shulan
python -m pytest tests/unit
```

按当前 [pyproject.toml](../pyproject.toml) 配置，`python -m pytest` 默认收集相同的 `tests/unit/`，也可作为全量命令；审核时应核对配置和实际收集范围。提交前运行的测试若与随后提交的内容完全一致，可记录对应提交，不因仅创建 commit 而重复执行。

审核人须核验作者或 CI 提供的测试记录；记录缺失、失败、对应版本不符或无法核对时，不得批准。需要本地复现时按上述命令运行，受环境限制未能验证不能填写“通过”。离线通过不代表真实模型、数据库、回调或部署验收通过；真实服务验证按任务要求另行记录，不替代全量离线测试。

### 2.4 跨模块依赖与交接

存在跨模块支持需求时，必须全部满足以下要求；不存在时在审核记录中明确说明。

- [ ] 根目录 `ISSUE.md` 已写明当前任务、所需支持、涉及模块或公共接口、对应负责人及验收条件。
- [ ] 已向对应协作人或开发者说明依赖与职责边界，有可核对的交接记录或负责人确认；仅登记 ISSUE 或在 PR 中 @ 对方不能代替交接。
- [ ] 支持部分由对应负责人通过独立分支和 PR 完成，当前分支没有代改其他模块。
- [ ] PR 关联了 ISSUE 条目及依赖 PR；所需支持已合入 `develop`，当前分支已同步基线并完成联调和全量离线单元测试。

## 3. 按改动内容补充检查

以下项目按实际改动判断适用性；不适用时说明原因，适用项未满足同样不得批准合并。

- [ ] **业务与回归**：实现符合本次需求及既有兼容约定；结合相关源码与测试核对正常路径、输入边界和错误处理。缺陷修复有能复现问题的回归验证，不能把目标方案当作当前实现。
- [ ] **Python 规范**：本次修改的 Python 文件通过贡献指南要求的 Ruff 检查与格式化验证，结果对应当前内容。
- [ ] **API 与文档**：外部接口行为改变时，当前契约 `docs/api/API.md`、示例、错误及异步交付说明同步；内部实现说明放入技术文档，历史快照不随普通修改回写。Markdown 格式、链接和命令示例有效。
- [ ] **配置与提交内容**：没有混入密钥、真实健康数据、缓存或无关文件；配置变化按 README 同步 `.env.example*` 并提供模板检查结果。自动化审核不读取其他私有 `.env*`。
- [ ] **协作与评审**：相关负责人已按需参与，作者已回应全部评审意见，阻塞问题已解决；合并前至少有一名非作者成员审核通过。

## 4. 审核结论与合并前复核

审核人必须明确给出以下一种结论，并绑定本次审核的源提交：

- **通过**：全部强制项及适用的补充检查均满足，证据可核对，没有遗留阻塞问题。
- **拒绝合并，待补齐后复审**：任一要求不满足、测试未通过或证据无法核对。逐项说明对应条款、具体问题、受影响文件及需要补齐的内容，不能使用“先合并后补测试”等附条件批准。

作者修改后，审核人必须重新按本文件复审，检查新增差异及其对原结论的影响；旧提交的批准不能直接用于新提交。合并操作前再次确认 PR 目标、当前源提交、测试记录、依赖状态及非作者审核均与通过结论一致。若 `develop` 已前进，须核对新增变更对本 PR 的影响；需要同步或解决冲突时，完成同步、全量测试和复审后再合并。

只有满足以上要求，才可由有权限的维护者通过 PR 合入 `develop`。拒绝合并表示当前版本不满足要求，作者补齐后可在原 PR 重新申请审核。

## 5. PR 审核记录模板

每次审核或复审在 PR 中填写以下记录；可复用上次内容，但必须更新提交、证据和结论。不得只粘贴空清单或勾选后不附依据。

```markdown
### develop 合并审核记录

- PR / 源分支：
- 审核人 / 审核时间：
- 本次审核源提交 SHA：
- 分支创建时的 develop 基线 / 来源依据：
- 本次审核时的 develop 提交 SHA：
- 本次职责范围：
- 关联 ISSUE 条目 / 依赖 PR（无则说明）：

| 审核项 | 结论（通过 / 不通过 / 不适用） | 核对依据或待补内容 |
|---|---|---|
| 分支基于 develop 创建、PR 目标正确 | | |
| 单模块或明确部分、完整差异符合范围 | | |
| 全量离线单元测试通过且对应当前内容 | | |
| 跨模块 ISSUE、负责人交接及依赖完成 | | |
| 适用的业务、Ruff、API、文档和配置检查 | | |
| 评审意见处理及非作者审核 | | |

- 全量测试命令 / 环境 / 完成时间：
- 测试对应提交 / 完整结果记录：
- 结果摘要（通过、失败、错误、跳过、预期失败及原因）：
- 未执行或未覆盖的其他验证：
- 阻塞问题与需补齐内容（无则写无）：
- 最终结论：通过 / 拒绝合并，待补齐后复审
```
