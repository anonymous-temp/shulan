# API 文档编辑手册

## 1. 目的与适用范围

本手册用于规范 `docs/api` 下对外 API 文档的编写、评审、发布和归档。接口的请求方式、参数、响应、回调、错误语义或兼容性规则发生变化时，均应按本手册同步维护文档。

## 2. 文档组织规则

### 2.1 当前版本

- `docs/api/API.md` 是项目唯一的当前 API 契约，必须包含所有已发布接口的完整说明。
- 调用方理解并完成接入所需的信息不得拆分到另一份同级 API 文档中。
- 专题设计、内部实现和调研材料可以另建文档，但不得代替 `API.md` 中的公开契约，也不得成为调用方必须阅读的前置材料。
- 第三方或公司内独立服务的原始接口资料统一存放在 `docs/integrations/<provider>/`。如果相关能力属于 Shulan 对外 API，即使请求由其他项目直接承载，也必须在 `API.md` 保留调用方所需的完整聚合契约，并明确独立 Base URL、责任边界和错误约定。

### 2.2 历史版本

- 已发布版本统一归档到 `docs/api/history/API_v<版本号>.md`，例如 `API_v0.9.1.md`。
- 历史文件是发布时 `API.md` 的完整快照，归档后原则上不得修改；如确需修正，只能修复排版或明显笔误，并在提交说明中注明。
- 发布新版本时，先把待发布的完整 `API.md` 校验通过，再复制为对应的历史文件。当前文档与本次归档文件的正文应一致。
- 不得使用 `REPORT_API_V1.md`、`NEW_API.md`、`API_FINAL.md` 等文件承载某个当前接口的必读契约。临时文档完成合并后应删除或迁入非契约类目录。

### 2.3 版本信息

`API.md` 顶部必须保留以下元信息：

```markdown
> **Version**: <语义化版本号>（<环境>）
>
> **Last Updated**: <YYYY年M月D日>
>
> **测试服**: `<测试环境地址>`
```

- 版本号采用 `主版本.次版本.修订号`。
- 不兼容变更提升主版本；向后兼容的新接口或新字段提升次版本；兼容性修正和文档勘误提升修订号。
- 日期必须是本次契约最后确认的日期，不使用预计发布日期。
- 地址、令牌、用户数据等示例不得包含生产凭据或真实隐私数据。

## 3. 文档结构

### 3.1 全文结构

`API.md` 按以下顺序组织：

1. 文档标题和版本信息。
2. 通用响应数据结构、公共状态码和公共约定。
3. 各业务接口章节。
4. 文件、流式传输、语音等跨接口限制或附录。

每个业务域使用二级标题，例如 `## AI问答接口`；同一业务域的具体端点使用三级标题，例如 `### 会话创建接口`。只有一个端点的业务域可以直接在二级标题下写接口内容。

### 3.2 单个接口的必备内容

每个接口至少应包含以下内容，并沿用已有文档的标题层级：

1. 接口用途和关键前置条件。
2. `接口信息`：请求路径、请求方法、`Content-Type`，必要时说明认证方式。
3. `请求参数`：参数名、类型、是否必填、约束与描述。
4. `请求示例`：可复制的 JSON、查询参数或表单示例；推荐同时提供 `curl`。
5. `响应示例`：成功响应及调用方需要处理的主要非成功响应。
6. `响应字段说明`：嵌套字段使用完整路径，例如 `data.items[].id`。
7. 异步接口的回调、轮询或事件协议。
8. `注意事项`：幂等性、超时、排序、分页、兼容性等无法从字段表直接得出的规则。

对于 SSE、WebSocket 或回调接口，还必须说明：

- 事件或回调的触发条件及顺序；
- 每种事件的完整字段结构；
- 正常结束、部分成功、失败和超时的判定方式；
- 重试、重复消息和断线恢复规则（如适用）。

## 4. 字段与示例写法

### 4.1 字段表

- 字段名用反引号包裹，并与代码中的大小写完全一致。
- 类型统一使用 `string`、`integer`、`number`、`boolean`、`object`、`array`、`null`；组合类型用 ` / ` 分隔。
- “必填”填写“是”“否”或“条件必填”。条件必填时必须在描述中写清条件。
- 枚举必须列出所有公开取值及语义；稳定错误码必须逐项列出。
- 空值规则必须明确区分 `null`、空字符串、`[]`、`{}` 和字段缺失。
- 不把内部类名、数据库字段、任务实现步骤写成对外契约，除非调用方确实需要依赖它。

### 4.2 示例

- `json` 代码块必须是合法 JSON，不得含注释、尾随逗号或占位省略号。
- API 文档中的请求与响应示例统一使用标准 `json` 代码块，必须能由标准 JSON 解析器直接读取；不得使用 JSONC 或在 JSON 代码块中添加注释。字段说明应写在代码块外或字段表中。
- `json` 代码块统一使用四个空格缩进，不使用制表符或两空格缩进。
- 普通段落必须保存在一个物理行内，不主动按列宽插入换行；标题、列表、表格、引用、代码块和显式硬换行不受此规则影响。
- 示例必须覆盖必填字段、关键嵌套结构和至少一个有意义的数组元素。
- UUID、时间、URL 和业务数据使用明显的虚构值，但格式必须真实可用。
- 请求表、示例、响应表和注意事项中的字段名及取值必须互相一致。

## 5. 内容边界与准确性

- API 文档只能记录与对外接口契约直接相关的内容，包括接口用途、路径、方法、认证、请求与响应字段、状态码、回调或事件协议，以及调用方必须遵守的限制。
- **禁止在 API 文档中编辑任何与对外接口无关的内容或技术实现细节。** 包括但不限于系统架构、内部模块与类、数据库或缓存设计、任务调度、算法与处理流水线、提示词与模型选择、第三方服务调用过程、部署运维、内部环境变量、调试过程和测试实现。
- 技术实现内容必须编辑在 `wiki/` 或对应的架构、设计、开发、部署、运维等技术文档中。确有必要说明实现背景时，API 文档最多提供一个指向相关技术文档的可选链接，不得把该链接作为调用方理解接口契约的前置条件。
- 环境变量名、内部服务地址和供应商调用细节仅在影响接入行为时出现；密钥值永不进入文档。
- 医疗、证据或模型生成接口必须明确数据来源、证据边界、不可推断内容和失败降级语义。
- 不能确认的行为先以代码、测试或接口负责人结论为准，不凭经验补写。
- 任何接口字段变化必须同步更新字段表、全部相关示例、错误处理和注意事项。

## 6. 变更与发布流程

1. 对照上一归档版本、当前实现和测试，列出新增、修改、废弃及删除内容。
2. 在 `API.md` 原有业务章节中完成修改，保持全文自包含。
3. 搜索旧路径、旧字段、旧状态和指向临时契约文档的链接，清除矛盾描述。
4. 运行 `python scripts/format_markdown.py`，再用 `python scripts/format_markdown.py --check` 校验普通段落、Markdown 结构和 JSON 缩进；同时检查相对链接。
5. 由接口实现者确认行为，由至少一名非实现者按文档尝试理解调用流程。
6. 确定版本号和更新日期；发布时将完整 `API.md` 复制到 `history/API_v<版本号>.md`。
7. 在提交或合并请求中说明接口兼容性、文档版本以及是否需要调用方改造。

## 7. 评审检查清单

发布前逐项确认：

- [ ] `API.md` 单独阅读即可完成全部当前接口的接入。
- [ ] 没有把必读契约拆到另一份同级文档。
- [ ] API 文档只包含对外接口契约，技术实现内容已放入 `wiki/` 或相关技术文档。
- [ ] 版本号、更新日期和环境地址正确。
- [ ] 每个端点的路径、方法、参数、示例和实际实现一致。
- [ ] 字段类型、必填条件、枚举和空值规则完整。
- [ ] 成功、部分成功、失败、超时及回调语义完整。
- [ ] 所有 JSON 示例均为标准 JSON，并可由标准 JSON 解析器直接读取。
- [ ] Markdown 表格、代码围栏和相对链接有效。
- [ ] 文档不包含密钥、连接串、真实患者信息、本地路径或堆栈。
- [ ] 新版本已在 `docs/api/history` 留存完整快照。

## 8. 禁止事项

- 禁止在 API 文档中写入与对外接口无关的内容或任何技术实现细节；此类内容必须放入 `wiki/` 或相关技术文档。
- 禁止仅在专题文档中更新契约而不更新 `API.md`。
- 禁止用“见代码”“见内部文档”代替公开字段定义。
- 禁止归档不完整的摘要版 API 文档。
- 禁止删除历史版本来覆盖版本差异。
- 禁止示例与字段表使用不同的字段名、类型或状态值。
- 禁止把未经确认的未来设计写成当前已支持能力。
